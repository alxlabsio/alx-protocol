# ADR-001: Keccak-256 For Deterministic Block Identity

This architecture decision records how Keccak-256 supports ALX v1 Block identity, test-vector stability, and EVM-compatible verification surfaces.

---

**Date:** 2025-04-15

## Context

ALX Protocol uses cryptographic hashing to derive deterministic Block identity from canonicalized content and parentHashes. The hash function defines how implementations derive Block hashes, how test vectors remain stable, and how optional checkpoint or proof systems verify ALX artifacts.

A stable hash function gives reviewers, implementers, and integrators a shared identity surface across SDKs, languages, storage systems, artifact packages, and product workflows.

## Decision

ALX v1 uses **Keccak-256** with legacy Keccak padding semantics for Block hashing.

This decision establishes a single hash function for canonical Block identity across reference implementations, conformance tests, canonical test vectors, artifact packages, verification receipts, and optional external verification surfaces.

## Rationale

1. **Stable Block identity.** Keccak-256 gives ALX a deterministic hash surface for Blocks, lineage, verification receipts, artifact packages, and canonical examples.

2. **EVM-compatible verification surfaces.** Keccak-256 aligns ALX with Ethereum and EVM-style hashing environments, allowing optional checkpoint, registry, and proof integrations to reuse the same hash semantics.

3. **Broad implementation support.** Keccak-256 libraries are available across TypeScript, Python, Rust, Go, and other implementation environments. Implementers can rely on mature cryptographic libraries rather than custom hashing code.

4. **Conformance-friendly behavior.** A single hash function keeps canonical test vectors stable and allows independent implementations to prove compatibility through identical Block hash outputs.

5. **Product integration readiness.** Applications can use the same Block identity across local SDKs, APIs, artifact packages, verification receipts, and optional infrastructure integrations.

## Design Options Reviewed

- **Keccak-256:** Supports deterministic Block identity, EVM-compatible verification surfaces, broad library availability, and stable conformance vectors. ALX v1 selects Keccak-256 as the hash function for canonical Block identity.

- **SHA-256:** Provides a strong general-purpose hash function with broad tooling availability. ALX v1 selects Keccak-256 to align Block identity with EVM-style checkpoint and proof ecosystems.

- **SHA3-256 / FIPS 202:** Provides the NIST-standardized SHA-3 variant with FIPS 202 padding semantics. ALX v1 selects legacy Keccak-256 so EVM-compatible verification systems and ALX test vectors share the same hash semantics.

- **BLAKE3:** Provides a high-performance hash function with strong developer ergonomics. ALX v1 selects Keccak-256 to prioritize ecosystem compatibility and stable first-version interoperability.

## Consequences

- ALX-compatible implementations derive Block hashes using Keccak-256 with legacy Keccak padding semantics.

- Canonical test vectors are pinned to Keccak-256 output.

- Hash-function changes require a new protocol version because Block identity, lineage references, verification receipts, artifact packages, and conformance outputs depend on hash stability.

- The TypeScript reference implementation can use `js-sha3` as the production Keccak dependency.

- Implementer documentation should explicitly distinguish Keccak-256 from SHA3-256 / FIPS 202 so implementations preserve the expected padding semantics.
